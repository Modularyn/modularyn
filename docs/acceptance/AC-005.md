# AC-005

Planning cases; see [corpus conventions](README.md). These are not execution results.

## AC-005-B01 — Observe ambient and independent transaction boundaries

- Family: `AC-005`
- Type: `boundary`
- Profiles: `reference`
- Requirements: `ARC-008`, `FND-008`, `FND-009`
- Layers: `real-provider-integration`
- Security dependencies: `AC-003`, `AC-004`

### Profile scope

- `reference`: G-02 PostgreSQL/EF Core persistence, non-security soft-delete filtering, direct SQL, transactions, concurrency and migrations. Tenant filtering depends on AC-004.

### Preconditions

- The adapter advertises joined, new and suppressed unit-of-work modes for one PostgreSQL database. The suppressed fixture uses an autocommitted direct write on an independent connection; each run uses separate outer and inner rows.

### Steps

1. For each mode write the outer row and the inner row, complete the inner scope, then roll back the outer scope.
2. Inspect committed rows using another connection.

### Expected outcome

- The outer row is absent after rollback in all three runs; joined mode also leaves no inner row.
- The completed new transaction and suppressed autocommitted write each retain their inner row. No result implies atomicity across databases.

### Evidence to retain

- Declared mode contract, transaction identifiers, completion callbacks and resulting row sets.

## AC-005-B02 — Check state at the commit boundary

- Family: `AC-005`
- Type: `boundary`
- Profiles: `website`
- Requirements: `ARC-008`, `FND-009`
- Layers: `real-provider-integration`
- Security dependencies: `AC-003`, `AC-004`

### Profile scope

- `website`: W PostgreSQL transactions and optimistic concurrency for content and contact state, with migration recovery on the single database.

### Preconditions

- A contact-1 submission writes its durable request and email intent in one transaction; the connection can be interrupted at controlled points.

### Steps

1. Run once with interruption immediately before commit and once immediately after database commit but before the caller receives success.
2. Inspect the request and intent using a fresh connection.

### Expected outcome

- The precommit run retains neither authoritative item.
- The postcommit run retains both; a client timeout does not change the recorded database outcome.

### Evidence to retain

- Fault timing, committed transaction identity and request/outbox counts for each run.

## AC-005-N01 — Reject stale writes and roll back a failed transaction

- Family: `AC-005`
- Type: `negative`
- Profiles: `reference`
- Requirements: `ARC-008`, `FND-009`, `FND-010`
- Layers: `real-provider-integration`
- Security dependencies: `AC-003`, `AC-004`

### Profile scope

- `reference`: G-02 PostgreSQL/EF Core persistence, non-security soft-delete filtering, direct SQL, transactions, concurrency and migrations. Tenant filtering depends on AC-004.

### Preconditions

- Two editors have item-1 at version 5; a unit of work can update item-1 and insert item-4.

### Steps

1. Save editor A's change and then submit editor B's original version.
2. In a fresh unit of work change item-1, then inject an insert failure before commit.

### Expected outcome

- The stale save reports a concurrency conflict and preserves A's value.
- The failed unit of work persists neither change and reports rolled back or failed, never committed.

### Evidence to retain

- Versioned requests, conflict response, fault point and independent database reads after both attempts.

## AC-005-N02 — Preserve the winner of concurrent website edits

- Family: `AC-005`
- Type: `negative`
- Profiles: `website`
- Requirements: `ARC-008`, `FND-009`, `FND-010`
- Layers: `real-provider-integration`
- Security dependencies: `AC-003`, `AC-004`

### Profile scope

- `website`: W PostgreSQL transactions and optimistic concurrency for content and contact state, with migration recovery on the single database.

### Preconditions

- Two Admin sessions read article-1 at the same version; both are prequalified for the operation.

### Steps

1. Save title First from one session.
2. Submit title Second with the stale token from the other session.
3. Force an outbox insert failure in a separate new save.

### Expected outcome

- The stale write returns a typed conflict and does not replace First.
- The separately failed save commits neither the proposed revision nor its outbox intent.

### Evidence to retain

- Requests and error responses, before/after revision hashes and database transaction outcomes.

## AC-005-P01 — Commit a unit of work and apply soft-delete filters

- Family: `AC-005`
- Type: `positive`
- Profiles: `reference`
- Requirements: `FND-008`, `FND-009`, `FND-010`
- Layers: `real-provider-integration`
- Security dependencies: `AC-003`, `AC-004`

### Profile scope

- `reference`: G-02 PostgreSQL/EF Core persistence, non-security soft-delete filtering, direct SQL, transactions, concurrency and migrations. Tenant filtering depends on AC-004.

### Preconditions

- PostgreSQL contains active rows item-1 and item-2 plus soft-deleted item-3 in the prequalified context. A declared direct-SQL access path uses the same application filter contract.

### Steps

1. Read through EF Core and the declared direct-SQL path.
2. In one unit of work update item-1 and create item-4; commit and reread through a new connection.

### Expected outcome

- Both reads return item-1 and item-2 and omit item-3.
- The new connection sees both committed changes; the completion callback reports committed once.

### Evidence to retain

- Provider/version inventory, query results, transaction trace and completion callback record.

## AC-005-R01 — Resume an interrupted migration without reseeding duplicates

- Family: `AC-005`
- Type: `recovery`
- Profiles: `reference`
- Requirements: `FND-011`
- Layers: `real-provider-integration`, `migration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`

### Profile scope

- `reference`: G-02 PostgreSQL/EF Core persistence, non-security soft-delete filtering, direct SQL, transactions, concurrency and migrations. Tenant filtering depends on AC-004.

### Preconditions

- A module migration adds a nullable field and an idempotent system seed to a populated PostgreSQL database; its recovery plan is recorded.

### Steps

1. Interrupt after a migration checkpoint and before completion is recorded.
2. Restart the coordinator, reconcile database and progress state, and run the migration and seed again.

### Expected outcome

- The coordinator reports the interrupted operation and follows the supported resume or forward-repair path.
- Existing rows survive, the new field has the planned shape, the seed exists once and migration progress reaches complete.

### Evidence to retain

- Checkpoint and migration history, repair/resume report, schema comparison and seed counts.

## AC-005-R02 — Recover a website schema migration interruption

- Family: `AC-005`
- Type: `recovery`
- Profiles: `website`
- Requirements: `FND-011`
- Layers: `real-provider-integration`, `migration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`

### Profile scope

- `website`: W PostgreSQL transactions and optimistic concurrency for content and contact state, with migration recovery on the single database.

### Preconditions

- A supported migration extends the article schema while old revisions and the active publication manifest remain present; a coordinated backup exists.

### Steps

1. Stop the migration process at its declared checkpoint.
2. Restart and reconcile progress, applying its supported resume or restore plan.
3. Read old and new revision fixtures and the active manifest.

### Expected outcome

- Recovery reaches a coherent schema version without losing historical revisions or the active manifest.
- Progress and any repair action are explicit; an untested reverse migration is never treated as recovery.

### Evidence to retain

- Migration and backup identities, interruption checkpoint, recovered schema/revision hashes and manifest reference checks.
