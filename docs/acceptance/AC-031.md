## AC-031-B01 — Rotate secrets and keys at their declared lifecycle edges

- Family: `AC-031`
- Type: `boundary`
- Profiles: `website`
- Requirements: `OPS-004`, `FND-006`
- Layers: `operational-recovery`, `unit`
- Security dependencies: `AC-002`, `AC-012`

### Profile scope

- `website`: W ASVS Level 2 applicability and production posture for the public, Admin, API, preview, import and contact surfaces: content security policy and framing on the shared origin, HTTPS, release and dependency provenance against the dependency register, secret, key and telemetry handling, hostile package and source input, backups, and container and network limits. No certification claim and no surface outside W.

### Preconditions

- The email transport credential, the data-protection key ring and the one-time-password seed key each have a current version and a documented rotation procedure. An Admin session and an encrypted seed predate rotation, and the declared retention of the previous data-protection key is recorded.

### Steps

1. Rotate the transport credential and send contact mail immediately before and after the previous credential is revoked.
2. Point the transport at an endpoint that presents an unverifiable certificate and send contact mail.
3. Rotate the key ring and present the earlier session cookie before and after the previous key's declared end.
4. Rotate the seed key and verify a one-time code for an account whose seed was encrypted under the previous key.

### Expected outcome

- Delivery succeeds under each valid credential and is a recorded delivery failure under the revoked one; the unverifiable certificate is a delivery failure with no unencrypted fallback.
- The earlier cookie is accepted until the previous key's declared end and refused after it.
- The earlier seed still verifies through the authorized key store after rotation.

### Evidence to retain

- Rotation records with key and credential versions, delivery states, cookie decisions per edge and code verification results, as evidence for TM-W-034, TM-G02-050 and TM-G02-056.

## AC-031-B02 — Show diagnostics to operators without exposing secret values

- Family: `AC-031`
- Type: `boundary`
- Profiles: `website`
- Requirements: `OPS-004`, `FND-038`, `OPS-006`
- Layers: `operational-recovery`, `unit`
- Security dependencies: `AC-003`, `AC-012`

### Profile scope

- `website`: W ASVS Level 2 applicability and production posture for the public, Admin, API, preview, import and contact surfaces: content security policy and framing on the shared origin, HTTPS, release and dependency provenance against the dependency register, secret, key and telemetry handling, hostile package and source input, backups, and container and network limits. No certification claim and no surface outside W.

### Preconditions

- Sentinel values are mounted as the database password, transport credential and Git source credential through deployment secret references. An anonymous probe and an operator holding diagnostics permission are available; probe semantics and diagnostic authorization are qualified by AC-025.

### Steps

1. Inspect every image layer and the image configuration for the sentinels.
2. Request liveness, readiness and diagnostics as the anonymous probe and as the operator, and export a diagnostic bundle as the operator.
3. Cause a database outage and a transport failure, then search logs, traces, metrics and the bundle for sentinels, session cookies and contact bodies, and inspect metric dimensions.

### Expected outcome

- No sentinel appears in an image layer or configuration; secrets arrive only through mounted references.
- Neither the probe's responses nor the operator's diagnostics and bundle contain a configuration value.
- No secret, cookie or contact body appears in telemetry or the bundle; metric dimensions carry no tenant or site labels, and inbound correlation values are bounded and confer no authority.

### Evidence to retain

- Layer inspection, probe and diagnostic responses per caller, and sentinel search results per output, as evidence for TM-W-054, TM-G02-047 and TM-G02-053.

## AC-031-N01 — Refuse unverified release artifacts, writable code and undeclared egress

- Family: `AC-031`
- Type: `negative`
- Profiles: `website`
- Requirements: `FND-001`, `ARC-013`, `OPS-021`
- Layers: `operational-recovery`
- Security dependencies: `AC-012`

### Profile scope

- `website`: W ASVS Level 2 applicability and production posture for the public, Admin, API, preview, import and contact surfaces: content security policy and framing on the shared origin, HTTPS, release and dependency provenance against the dependency register, secret, key and telemetry handling, hostile package and source input, backups, and container and network limits. No certification claim and no surface outside W.

### Preconditions

- The release record names the image and migration-bundle digests with their provenance and software bills of materials. A rebuilt image carries the release tag with a different digest, and a migration bundle lacks provenance. The running deployment allows egress only to the database, the email transport and allowlisted Git hosts.

### Steps

1. Attempt deployment of the rebuilt image by tag and of the unattested bundle.
2. Inside the running container, inspect the process user and capabilities, and attempt writes to the application code paths.
3. From the application process, attempt outbound connections to an unlisted external host and to an internal network service.

### Expected outcome

- Both deployments are refused before any migration, and the running release is unchanged.
- The process runs as a non-root user with no added capabilities; code-path writes fail, and only the Files, key and temporary volumes are writable.
- Undeclared egress is denied and logged, and normal operation does not depend on it.

### Evidence to retain

- Deployment refusals with digest comparisons, process and filesystem inspection, and egress attempt results, as evidence for TM-W-050, TM-W-053 and TM-W-055.

## AC-031-N02 — Block hostile package and documentation input before planning

- Family: `AC-031`
- Type: `negative`
- Profiles: `website`
- Requirements: `OPS-005`, `OPS-004`
- Layers: `unit`, `real-provider-integration`
- Security dependencies: `AC-003`, `AC-012`

### Profile scope

- `website`: W ASVS Level 2 applicability and production posture for the public, Admin, API, preview, import and contact surfaces: content security policy and framing on the shared origin, HTTPS, release and dependency provenance against the dependency register, secret, key and telemetry handling, hostile package and source input, backups, and container and network limits. No certification claim and no surface outside W.

### Preconditions

- Each fixture package carries one violation: markup in a title, a template delimiter in block text, an unsafe URI scheme in a link field, a credential-like assignment in a Markdown body, a symbolic link, an executable mode, an undeclared file, or nesting beyond the declared bound.
- Package and documentation sources each reference a submodule, a redirect to an unlisted host and a large-file pointer on an unlisted host. The private source credential is a deployment secret reference.

### Steps

1. Dry run each package, and run documentation intake for each source.
2. Search plans, reports, logs, errors and audit records for the source credential and the credential-like value.

### Expected outcome

- Each package is blocked before planning with a diagnostic naming its rule and location, and nothing is written or fetched.
- Acquisition and intake refuse the submodule, the redirect and the unlisted large-file host within the declared transfer, object-count and time bounds.
- Neither the credential nor the credential-like value appears in any output, and the secret finding is reported with its value redacted.

### Evidence to retain

- Per-fixture diagnostics, fetch logs with bounds and destinations, write inventories and search results, as evidence for TM-W-035, TM-W-037, TM-W-036, TM-W-044 and TM-W-045.

## AC-031-N03 — Contain active content on the shared canonical origin

- Family: `AC-031`
- Type: `negative`
- Profiles: `website`
- Requirements: `OPS-005`, `OPS-001`
- Layers: `api-contract`, `ui`
- Security dependencies: `AC-003`

### Profile scope

- `website`: W ASVS Level 2 applicability and production posture for the public, Admin, API, preview, import and contact surfaces: content security policy and framing on the shared origin, HTTPS, release and dependency provenance against the dependency register, secret, key and telemetry handling, hostile package and source input, backups, and container and network limits. No certification claim and no surface outside W.

### Preconditions

- author-1 can save a draft whose title, block text and image alt text contain markup and script-like text. The canonical origin serves public pages, error pages, media, health, Admin and preview responses, and a fixture page on an unrelated origin can frame any of them.

### Steps

1. Publish the draft, then render it on the public site, in preview and in the Admin editor.
2. Request one response of each class, including a not-found page, a media response and a health response, and inspect its headers.
3. Load an Admin page and a preview page inside the fixture page's frame.

### Expected outcome

- Every content-derived value renders as encoded text in each context; no element that the renderers do not declare is emitted, and no script runs.
- Every response carries a content security policy that forbids inline script; Admin and preview responses also carry no-sniff and strict referrer policies.
- The framed Admin and preview pages do not render, because their responses forbid framing.

### Evidence to retain

- Rendered output per context with encoding inspection, browser script-execution observations, header captures per response class and framing results, as evidence for TM-W-002 and TM-W-017.

No certification claim and no surface outside W.

### Preconditions

### Steps

1. Assess each ASVS Level 2 requirement for the public, Admin, API, preview, import and contact surfaces, mapping it to threat-model controls and to the acceptance cases of the family that plans each control, or recording why it does not apply.

## AC-031-P02 — Deploy a clean release verified against its provenance and the dependency register

- Family: `AC-031`
- Type: `positive`
- Profiles: `website`
- Requirements: `PRD-002`, `FND-001`, `OPS-020`, `OPS-004`
- Layers: `operational-recovery`, `unit`
- Security dependencies: `AC-002`, `AC-012`

### Profile scope

- `website`: W ASVS Level 2 applicability and production posture for the public, Admin, API, preview, import and contact surfaces: content security policy and framing on the shared origin, HTTPS, release and dependency provenance against the dependency register, secret, key and telemetry handling, hostile package and source input, backups, and container and network limits. No certification claim and no surface outside W.

### Preconditions

- The release record lists the image and migration-bundle digests, provenance, software bills of materials and the deployment lock manifest. The dependency register at the release commit records each dependency's exact version, license, clearance and advisory review, and a clean environment holds the deployment's one-time bootstrap secret.

### Steps

1. Verify provenance and the bills of materials against the release record, then deploy the image and migration bundle by digest into the clean environment.
2. Compare every component in the bills of materials and lock manifest with the register's entries, versions, licenses, clearances and advisory review.
3. Scan the repository at the release commit and every release artifact for secrets.
4. Create the first administrator with the bootstrap secret, then call the setup path again.

### Expected outcome

- Deployment proceeds only with matching digests and provenance, and the running image digest equals the release record.
- Every shipped component is in the register at its exact version and is cleared, or is flagged with a recorded redistribution review; no unlisted component ships.
- The secret scans report no finding.
- The setup path closes once the administrator exists.

### Evidence to retain

- Provenance and digest verification, the component-to-register comparison, secret scan reports and bootstrap traces, as evidence for TM-W-050, TM-G02-047 and TM-W-014.

## AC-031-R01 — Restore encrypted backups only with separately held keys

- Family: `AC-031`
- Type: `recovery`
- Profiles: `website`
- Requirements: `OPS-004`, `FND-039`, `OPS-006`
- Layers: `operational-recovery`
- Security dependencies: `AC-002`, `AC-012`

### Profile scope

- `website`: W ASVS Level 2 applicability and production posture for the public, Admin, API, preview, import and contact surfaces: content security policy and framing on the shared origin, HTTPS, release and dependency provenance against the dependency register, secret, key and telemetry handling, hostile package and source input, backups, and container and network limits. No certification claim and no surface outside W.

### Preconditions

- Encrypted coordinated backup set b-1 and its key material are in separate stores limited to the recovery role, and the data-protection key ring and seed key are backed up apart from data exports. editor-1 holds every minimal Admin permission but not the recovery role.

### Steps

1. As editor-1, attempt to read b-1 and its key store; as the recovery role, restore b-1 with its keys into an isolated deployment.
2. Attempt the restore once without the key store and once with b-1 altered after encryption.
3. On the restored deployment, inspect the account store and sign in with a one-time code and with a passkey.

### Expected outcome

- Only the recovery role reaches b-1 and its keys.
- Without the keys the set cannot be decrypted, and the altered set fails integrity verification before any data is applied.
- The restored account store holds only salted adaptive verifiers, encrypted seeds and integrity-tagged passkey records, and both sign-ins verify through the restored key ring and seed key.

### Evidence to retain

- Access decisions, restore attempt outcomes, account-store inspection with values reduced to digests, and sign-in results, as evidence for TM-W-046, TM-G02-050, TM-G02-055, TM-G02-056 and TM-G02-058.

## AC-031-R02 — Rotate exposed deployment secrets and confirm the old values are refused

- Family: `AC-031`
- Type: `recovery`
- Profiles: `website`
- Requirements: `OPS-004`, `FND-006`, `ARC-013`
- Layers: `operational-recovery`, `real-provider-integration`
- Security dependencies: `AC-002`, `AC-012`

### Profile scope

- `website`: W ASVS Level 2 applicability and production posture for the public, Admin, API, preview, import and contact surfaces: content security policy and framing on the shared origin, HTTPS, release and dependency provenance against the dependency register, secret, key and telemetry handling, hostile package and source input, backups, and container and network limits. No certification claim and no surface outside W.

### Preconditions

- An incident fixture declares the transport credential, the Git source credential and the database password exposed while contact mail is queued.

### Steps

1. Rotate each secret through its documented procedure, revoke the exposed values at their providers, and restart the container with the new mounted secrets.
2. From a separate client, attempt delivery, Git acquisition and a database connection with each exposed value.
3. Acquire a private package snapshot and a documentation revision with the new credential, and attempt a write to the source with it.
4. Search the repository, image, logs, plans and reports for the old and new values.

### Expected outcome

- Each exposed value is refused by its provider, and the deployment resumes with the new values and delivers the queued mail once.
- The new Git credential reads but cannot write.
- Neither old nor new values appear in any searched artifact.

### Evidence to retain

- Rotation and revocation records, refused attempts, delivery and acquisition results, and search reports, as evidence for TM-W-054, TM-W-045 and TM-G02-047.
