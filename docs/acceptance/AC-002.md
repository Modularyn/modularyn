## AC-002-B01 — Throttle password guessing at the source threshold without locking out the owner

- Family: `AC-002`
- Type: `boundary`
- Profiles: `website`
- Requirements: `OPS-003`, `MOD-001`, `MOD-002`
- Layers: `api-contract`, `operational-recovery`
- Security dependencies: `AC-012`

### Profile scope

- `website`: W minimal Admin sign-in with a password plus a second factor or a passkey, account recovery, session revocation, stored credential forms, guessing and lockout resistance, and first-administrator bootstrap on the canonical origin. Registration, external login, passwordless links and shared-account tenant membership are outside W.

### Preconditions

- admin-1 has a password, a one-time-password authenticator and a passkey. Sources src-1, src-2 and src-3 are distinct. The release's declared per-source threshold N, per-account delay schedule and cap, and operator alert threshold for password verification are recorded before running.

### Steps

1. Starting from fresh fixture state, submit N minus one wrong passwords for admin-1 from src-1, then the correct password and one-time code.
2. Starting from fresh fixture state again, submit N wrong passwords from src-1, alternating between the minimal Admin sign-in page and direct calls to the sign-in API, then the correct password and code from src-1 and from src-2.
3. From src-2 and src-3 in turn, continue wrong passwords for admin-1 until the per-account delay reaches its cap and the alert threshold is crossed, then sign in with admin-1's passkey from src-3.
4. Have the recovery role run the documented, audited unlock procedure, then sign in from src-3 with the correct password and code.

### Expected outcome

- After N minus one failures sign-in still succeeds. After the Nth failure src-1 is blocked by source, so its correct attempt is refused, while src-2 is not blocked; attempts through the minimal Admin and the direct sign-in API count together.
- The per-account delay follows the declared schedule and stops at its cap; no number of failures produces indefinite lockout, and passkey sign-in stays available while password attempts are delayed.
- Crossing the alert threshold notifies operators once; the unlock is audited and returns password verification to its normal delay.

### Evidence to retain

- Per-attempt source, account, counter, applied delay and outcome; alert, notification and unlock audit records; and the declared threshold values, as evidence for TM-G02-015 and TM-W-059.

## AC-002-B02 — Expire sessions and recent authentication at their declared edges

- Layers: `api-contract`, `ui`

Registration, external login, passwordless links and shared-account tenant membership are outside W.

### Preconditions

- The fixture deployment reads time through the injectable clock. The declared session idle timeout I, absolute lifetime A and recent-authentication window T are recorded before running.
- Each row uses a fresh fixture account that holds rollback permission, a passkey and a one-time-password authenticator.

### Steps

1. Leave one session idle for I minus one second and another for I plus one second, then issue an Admin read with each.
2. Keep a third session active with requests spaced below I until A minus one second and A plus one second after sign-in.
3. At T minus one second and T plus one second after the last authentication, request enrollment of a second passkey, removal of the one-time-password authenticator and a rollback.

### Expected outcome

- Each request inside a limit succeeds; each request past it is refused, and the server-side session record shows the ended state and its reason.
- Inside T, enrollment, removal and rollback proceed with their notification and audit records; past T, each requires reauthentication before any change.

### Evidence to retain

- Clock offsets, session records, per-edge request outcomes, reauthentication prompts and notification and audit records, as evidence for TM-G02-016 and TM-W-013.

## AC-002-N01 — Refuse password-only, alias-host, host-variant and closed bootstrap paths

- Type: `negative`
- Profiles: `website`
- Requirements: `MOD-001`, `MOD-002`, `OPS-003`
- Layers: `api-contract`, `ui`
- Security dependencies: `AC-004`, `AC-031`

### Profile scope

- `website`: W minimal Admin sign-in with a password plus a second factor or a passkey, account recovery, session revocation, stored credential forms, guessing and lockout resistance, and first-administrator bootstrap on the canonical origin. Registration, external login, passwordless links and shared-account tenant membership are outside W.

### Preconditions

- admin-1 has a password and a one-time-password authenticator. alias-1 is a verified alias of the single site with an internationalized label, so it has a Unicode form and a punycode form; the deployment declares one proxy. An administrator exists, and the deployment's one-time bootstrap secret was consumed at installation.

### Steps

1. Submit admin-1's correct password, skip the second factor, and call an Admin API and an Admin page with the cookies the browser then holds.
2. Request the Admin sign-in, preview and API namespaces in a browser and with a direct client on alias-1 and on each of its variants: changed letter case, a trailing dot, an explicit port, and its other Unicode or punycode form.
3. Send the same requests to alias-1 with a forwarded-host value naming the canonical host, from a source that is not the declared proxy.
4. With a direct client, request the same namespaces on the canonical host with changed letter case, with a trailing dot and with an explicit port.
5. Call the first-administrator setup path with no secret, with the consumed secret and with a malformed secret.

### Expected outcome

- No Admin session or Admin-scoped cookie exists after the password step alone, and both calls are refused as unauthenticated.
- Neither alias-1, any of its variants, nor the forwarded-host request answers a reserved namespace or sets a cookie; Admin cookies carry a host prefix and are issued only on the canonical origin.
- Each canonical-host variant is either refused or redirected to the exact canonical origin, and no response to a variant sets a cookie.
- Each bootstrap attempt receives the same response as an absent route, and the account inventory is unchanged.

### Evidence to retain

- Request and response traces with cookie jars for each row and host variant, and account inventories before and after, as evidence for TM-W-010, TM-W-009 and TM-W-014.

## AC-002-N03 — Throttle one-time-code and recovery-code guessing past their declared limits

- Family: `AC-002`
- Type: `negative`
- Profiles: `website`
- Requirements: `OPS-003`, `MOD-001`, `MOD-002`
- Layers: `unit`, `api-contract`
- Security dependencies: `AC-012`

### Profile scope

- `website`: W minimal Admin sign-in with a password plus a second factor or a passkey, account recovery, session revocation, stored credential forms, guessing and lockout resistance, and first-administrator bootstrap on the canonical origin. Registration, external login, passwordless links and shared-account tenant membership are outside W.

### Preconditions

- admin-1 has a one-time-password authenticator and unused recovery codes, and each run starts from a pending sign-in that has passed the password step; unknown-1 is not an account. Sources src-1, src-2 and src-3 are distinct.
- For one-time-code and for recovery-code verification, the release's declared per-source limit, per-account limit, the block or delay each applies at its limit, and the uniform-response latency tolerance E are recorded before running.

### Steps

1. From fresh fixture state, submit wrong one-time codes for admin-1 from src-1, alternating between the minimal Admin sign-in page and direct calls to the sign-in API, up to the per-source limit, then one more wrong code and the current correct code from src-1, timing every response.
2. Continue wrong one-time codes from further sources, each below its per-source limit, until the per-account limit is reached; then, from a source still below its limit, submit the current correct code once before the applied delay elapses and once after it.
3. Repeat both steps with recovery codes in place of one-time codes, from fresh fixture state.
4. From src-3, alternate wrong passwords for admin-1 and for unknown-1 an equal number of times, staying below the per-source limit.

### Expected outcome

- Attempts through the minimal Admin and through the direct sign-in API count against the same limits, so neither path bypasses them.
- At each per-source limit, src-1's next attempt is blocked, and the correct code it then submits is refused without being verified.
- At each per-account limit, further attempts from any source are delayed by at least the declared delay. The correct code submitted before the delay elapses is refused, and a refused recovery code is not consumed; the one submitted after the delay succeeds, so the owner is not locked out indefinitely.
- Every attempt past a limit is either refused without verification or answered no sooner than the declared delay after the preceding attempt, so no run verifies more codes per window than the declared limits allow.
- Unknown-account and wrong-password responses match in status and body, and their median latencies differ by no more than E.

### Evidence to retain

- Per-attempt kind, source, counter, verification flag, applied delay and response time, with the declared limits, delays and tolerance, as evidence for TM-G02-015 and TM-W-059.

## AC-002-N04 — Reject credential records changed outside enrollment

- Family: `AC-002`

- Profiles: `website`

- Security dependencies: `AC-012`, `AC-031`

### Profile scope

- `website`: W minimal Admin sign-in with a password plus a second factor or a passkey, account recovery, session revocation, stored credential forms, guessing and lockout resistance, and first-administrator bootstrap on the canonical origin. Registration, external login, passwordless links and shared-account tenant membership are outside W.

### Preconditions

- admin-1 and editor-1 each have an enrolled passkey, and admin-1 also has a one-time-password seed with a known sentinel value. A database fixture can edit account rows directly, and the account tables can be exported without access to the authorized key store.

### Steps

1. In PostgreSQL, replace the public key in admin-1's passkey record with editor-1's, then attempt to sign in as admin-1 with editor-1's authenticator.
2. Restore the record, rebind editor-1's passkey record to admin-1's account identifier, and attempt the same sign-in.
3. Export the account tables without the key store and examine every seed column.
4. Search a database dump, logs, telemetry, a backup set after the recovery role decrypts it, and every export the release produces for the sentinel seed in plaintext and in its base32 and hexadecimal encodings.

### Expected outcome

- Each altered record fails integrity verification before it is trusted; no session is issued, and the failure is audited.
- The export holds only ciphertext seeds tagged with key versions; no seed is readable from the database alone.
- The sentinel seed appears in none of the searched outputs in any of those forms.

### Evidence to retain

- Descriptions of each altered row, sign-in refusals, integrity-verification and audit records, the seed-column inspection with values reduced to digests, and the sentinel search results, as evidence for TM-G02-058 and TM-G02-056.

## AC-002-N05 — Throttle recovery initiation and refuse reused or expired recovery proofs

- Family: `AC-002`
- Type: `negative`
- Profiles: `website`
- Requirements: `OPS-003`, `MOD-001`, `MOD-002`
- Layers: `unit`, `api-contract`
- Security dependencies: `AC-012`

### Profile scope

- `website`: W minimal Admin sign-in with a password plus a second factor or a passkey, account recovery, session revocation, stored credential forms, guessing and lockout resistance, and first-administrator bootstrap on the canonical origin. Registration, external login, passwordless links and shared-account tenant membership are outside W.

### Preconditions

- admin-1 has a one-time-password authenticator and unused recovery codes, with one consumed code; unknown-1 is not an account. Sources src-1, src-2 and src-3 are distinct, and the outbound message log of the bounded delivery environment is captured.
- The release's declared per-source and per-account limits and delays for recovery initiation, and the recovery-token lifetime, are recorded before running.

### Steps

1. From fresh fixture state, initiate recovery for admin-1 from src-1 up to its per-source limit and once more, timing every response.
2. Continue initiation for admin-1 from src-2 and src-3, each below its per-source limit, up to the per-account limit and once more; then initiate once for unknown-1 from src-3.
3. Present the consumed recovery code, use one issued recovery token twice, and present another token after its declared lifetime.
4. Submit one unused recovery code in two concurrent attempts from separate clients.
5. With a fresh token, attempt to complete recovery while removing admin-1's second factor in the same flow, then complete it with the token and a current one-time code.

### Expected outcome

- At each limit the next initiation is throttled: no token is issued and no message is sent, and every initiation past a limit is answered no sooner than its declared delay.
- Per-source throttling may answer with a throttling status, but per-account throttling returns the same status and body as an accepted initiation, and initiation for unknown-1 matches an accepted one and sends nothing, so no response reveals whether an account exists.
- The consumed code, the second use of the token and the expired token are refused.
- Exactly one concurrent attempt succeeds and the code is consumed once; the other is refused.
- Recovery through the token alone cannot remove the second factor; when recovery completes with the remaining factor, all admin-1 sessions end and the account is notified.

### Evidence to retain

- Per-initiation source, account, counter, applied delay and response time; token issuance and outbound message records; token and code states; and session records and notifications, as evidence for TM-W-011 and TM-G02-057.
