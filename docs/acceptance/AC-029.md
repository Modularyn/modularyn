# AC-029

Planning cases; see [corpus conventions](README.md). These are not execution results.

## AC-029-B01 — Reconcile effects that straddle the backup boundary

- Family: `AC-029`
- Type: `boundary`
- Profiles: `website`
- Requirements: `OPS-013`, `CMS-022`, `FND-021`, `FND-022`
- Layers: `real-provider-integration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`, `AC-012`, `AC-031`

### Profile scope

- `website`: W coordinated restore of PostgreSQL, schemas, revisions, immutable manifests and filesystem Files into a recovery deployment prequalified by AC-004; derived cache rebuild and publication/email reconciliation only.

### Preconditions

- The backup captures one scheduled publication and one queued contact email. After capture, publication activation and transport acceptance occur in the original deployment and their operation identities are retained.

### Steps

1. Restore the snapshot with execution held for reconciliation.
2. Compare schedule/publication and email identities with their postbackup outcomes before resuming.
3. Inspect each work item's disposition.

### Expected outcome

- Already completed activation and accepted transport work are recognized under their original identities.
- Uncertain outcomes remain explicit; resumption never blindly replays an external effect merely because the restored queue says pending.

### Evidence to retain

- Backup cutoff, postbackup outcome records, per-item reconciliation decisions and resumed-effect counts.

## AC-029-N01 — Refuse an inconsistent backup set

- Family: `AC-029`
- Type: `negative`
- Profiles: `website`
- Requirements: `OPS-013`, `CMS-022`
- Layers: `real-provider-integration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`, `AC-012`, `AC-031`

### Profile scope

- `website`: W coordinated restore of PostgreSQL, schemas, revisions, immutable manifests and filesystem Files into a recovery deployment prequalified by AC-004; derived cache rebuild and publication/email reconciliation only.

### Preconditions

- A valid backup set is copied into two faulty fixtures: one omits a historically referenced file version and one combines a newer database snapshot with older Files.

### Steps

1. Restore and validate each fixture before declaring it ready.

### Expected outcome

- Each restore reports the exact missing or mismatched reference and remains incomplete.
- It cannot silently drop historical content or advertise successful readiness from a partial set.

### Evidence to retain

- Two backup inventories, failed reference/digest checks and readiness disposition.

## AC-029-P01 — Restore authoritative website state and historical references

- Family: `AC-029`
- Type: `positive`
- Profiles: `website`
- Requirements: `OPS-013`, `CMS-022`, `FND-024`
- Layers: `real-provider-integration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`, `AC-012`, `AC-031`

### Profile scope

- `website`: W coordinated restore of PostgreSQL, schemas, revisions, immutable manifests and filesystem Files into a recovery deployment prequalified by AC-004; derived cache rebuild and publication/email reconciliation only.

### Preconditions

- A coordinated backup includes type versions 1 and 2, current and historical revisions/manifests, media versions and their digest inventory. The recovery deployment and external-effect controls have been qualified separately.

### Steps

1. Restore PostgreSQL and Files from the same backup set.
2. Validate every manifest-to-revision-to-schema/renderer/media reference and read current and historical fixtures.
3. Rebuild derived delivery cache.

### Expected outcome

- All restored authoritative identities and bytes match the coordinated inventory.
- Current delivery selects the restored active manifest; historical versions remain resolvable, and derived cache agrees after rebuild.

### Evidence to retain

- Backup-set identity, complete reference/integrity report, current/historical reads and rebuild results.

## AC-029-R01 — Resume an interrupted restore without serving a mixed state

- Family: `AC-029`
- Type: `recovery`
- Profiles: `website`
- Requirements: `OPS-013`, `CMS-022`, `FND-024`
- Layers: `real-provider-integration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`, `AC-012`, `AC-031`

### Profile scope

- `website`: W coordinated restore of PostgreSQL, schemas, revisions, immutable manifests and filesystem Files into a recovery deployment prequalified by AC-004; derived cache rebuild and publication/email reconciliation only.

### Preconditions

- A complete backup and its expected digests are available. The restore can stop after database restore and midway through filesystem recovery.

### Steps

1. Interrupt at both checkpoints in independent runs.
2. Restart the restore, verify recovered objects and complete missing ones before rebuilding cache and declaring readiness.

### Expected outcome

- Partial restores retain a visible incomplete state and never claim coherent delivery.
- Repeated recovery verifies or restores each item without corrupting completed ones; final state matches the same backup set.

### Evidence to retain

- Checkpoint/progress records, per-object recovery results, digest comparison and final readiness/read observations.

## AC-029-R02 — Rebuild derived state and resume reconciled schedules and email

- Family: `AC-029`
- Type: `recovery`
- Profiles: `website`
- Requirements: `OPS-013`, `CMS-022`, `FND-021`, `FND-022`, `FND-024`
- Layers: `real-provider-integration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`, `AC-012`, `AC-031`

### Profile scope

- `website`: W coordinated restore of PostgreSQL, schemas, revisions, immutable manifests and filesystem Files into a recovery deployment prequalified by AC-004; derived cache rebuild and publication/email reconciliation only.

### Preconditions

- Authoritative restore is complete; cache is stale, one publication is due, one email is known unsent and one has an unresolved transport outcome.

### Steps

1. Rebuild cache from the active manifest.
2. Apply the declared schedule misfire policy and dispatch only the known-unsent contact.
3. Resolve the uncertain transport identity before permitting its final disposition.

### Expected outcome

- Cache converges without changing authoritative history; the due publication receives one recorded outcome.
- Known-unsent work progresses once and ambiguous work stays visibly held until resolved, with no uncontrolled resend.

### Evidence to retain

- Cache generations, misfire decisions, email reconciliation records and effect counts after recovery.
