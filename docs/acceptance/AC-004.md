## AC-004-B01 — Isolate context at worker reuse and asynchronous continuation edges

- Family: `AC-004`
- Type: `boundary`
- Profiles: `reference`
- Requirements: `FND-013`, `ARC-005`, `FND-014`
- Layers: `isolation`, `unit`
- Security dependencies: `AC-003`

### Profile scope

- `reference`: G-02 shared-database tenancy with adversarial cross-tenant identifiers through queries, references, imports, Files, cache, jobs and events, host and tenant-administrator scope, and execution context that cannot leak between units of work. Database-per-tenant and hybrid placement are outside the reference tuple.

### Preconditions

- One worker and one pooled database context serve consecutive units of work for tenant-A, then tenant-B, then a host-scope maintenance unit. A tenant-A request awaits a continuation that resumes while a tenant-B request runs on the same thread pool.

### Steps

1. Run the three units consecutively on the same worker, recording ambient tenant, actor and transaction state at entry.
2. Resume tenant-A's continuation during tenant-B's request.
3. Fail a tenant-A unit mid-transaction, then run a tenant-B unit on the same worker.

### Expected outcome

- Each unit starts with no tenant, actor or transaction from its predecessor, and the host-scope unit inherits neither tenant.
- The continuation keeps tenant-A's context while tenant-B's request keeps its own.
- After the failure, no tenant-A state, transaction or cache entry is visible to tenant-B's unit.

### Evidence to retain

- Context snapshots at the entry and exit of each unit, continuation traces and post-failure inspection, as evidence for TM-G02-026.

### Preconditions

## AC-004-B03 — Accept only canonical tenant and site identifiers and hosts at the format edge

- Requirements: `FND-013`, `FND-018`, `OPS-002`
- Layers: `unit`, `isolation`, `api-contract`
- Security dependencies: `AC-003`

### Profile scope

- `website`: W one tenant and one site: forged tenant and site identifiers in content, Files, imports, routes, cache, jobs and events, and on Admin, preview and public paths, fail as cross-tenant identifiers do. Decoy rows, files and cache entries stand in for absent tenants; multisite governance is outside W.

### Preconditions

- The deployment has tenant-1, site-1, the canonical origin and verified alias-1. Variants of site-1's identifier differ only in letter case, surrounding whitespace, percent-encoding or an appended separator; variants of alias-1's host differ only in letter case or a trailing dot.

### Steps

1. As editor-1, submit content, preview and route requests carrying site-1's canonical identifier and each identifier variant.
2. Request a public route with each host variant of alias-1.

### Expected outcome

- Host variants that are equivalent under DNS rules resolve consistently to alias-1 for public routes, and none resolves to another host binding or to the canonical origin.

### Evidence to retain

## AC-004-N01 — Reject forged tenant candidates at ingress

- Layers: `isolation`, `api-contract`
- Security dependencies: `AC-002`, `AC-003`

### Profile scope

Database-per-tenant and hybrid placement are outside the reference tuple.

### Preconditions

- user-a is a member of tenant-A only. The deployment declares one proxy and the configured domains of tenant-A and tenant-B, and an unknown well-formed tenant identifier is prepared.

### Steps

1. As user-a on tenant-A's domain, call an item endpoint with tenant-B, and separately the unknown identifier, in a route value, a request header and a body field.
2. Send requests whose forwarded host and scheme name tenant-B's domain, once directly from a client and once through the declared proxy.
3. Send a request with an unconfigured host name, and a sign-in request whose return address names another origin.

### Expected outcome

- No forged candidate becomes the effective tenant; each is refused before data access with the same contract for existing and unknown tenants.
- Forwarded values from a non-proxy source are ignored; through the declared proxy, tenant-B's domain still requires membership, which user-a lacks.
- The unconfigured host is refused, and the return address is refused or replaced by a relative path.

### Evidence to retain

- Per-row candidate, effective context and decision, and request and response headers, as evidence for TM-G02-025 and TM-G02-006.

## AC-004-N02 — Refuse cross-tenant identifiers in data, references, imports and Files

- Family: `AC-004`
- Type: `negative`
- Profiles: `reference`
- Requirements: `OPS-002`, `FND-016`, `ARC-016`, `FND-014`
- Layers: `isolation`, `real-provider-integration`, `api-contract`

### Profile scope

- `reference`: G-02 shared-database tenancy with adversarial cross-tenant identifiers through queries, references, imports, Files, cache, jobs and events, host and tenant-administrator scope, and execution context that cannot leak between units of work. Database-per-tenant and hybrid placement are outside the reference tuple.

### Preconditions

- user-a holds full item and file permissions in tenant-A. Identifiers of tenant-B's item-b1, file-b1 and a download grant on file-b1 are known to the test, and the fixture module declares a batch import and a direct-SQL report query.

### Steps

1. As user-a, read, update and delete item-b1 by identifier; create a tenant-A item whose reference names item-b1; and filter, sort, count and export using item-b1's key.
2. Run the direct-SQL report query and a bulk update in tenant-A's context and inspect the executed predicates.
3. Import a tenant-A batch whose rows name item-b1 and name tenant-B as owner and target.
4. Download file-b1 by identifier, with tenant-B's grant, and through a storage location derived from its identity.

### Expected outcome

- Every item-b1 operation and reference is refused exactly as for a nonexistent identifier; lists, counts and exports contain only tenant-A rows.
- The direct-SQL query and bulk update carry the tenant predicate and touch no tenant-B row.
- The import rejects the foreign identifiers and writes nothing for tenant-B.
- None of the three requests serves file-b1; the gateway checks tenant, version and purpose.

### Evidence to retain

- Per-request decisions, executed SQL with parameters, tenant-B row and file inventories before and after, and gateway decisions, as evidence for TM-G02-020, TM-G02-021, TM-G02-029 and TM-G02-044.

### Preconditions
