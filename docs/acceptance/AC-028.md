## AC-028-B01 — Distinguish a first release from an upgrade claim

- Family: `AC-028`
- Type: `boundary`
- Profiles: `website`
- Requirements: `REL-001`, `REL-005`, `REL-006`
- Layers: `real-provider-integration`, `migration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`, `AC-012`, `AC-031`

### Profile scope

- `website`: W previous-release upgrade and version-1 content-package portability, including stable mappings, dependencies, collisions, interruption and failed activation. First-release absence of a predecessor is recorded explicitly.

### Preconditions

- One release fixture has a recorded W predecessor and another is the initial W release with no predecessor; their release histories are retained.

### Steps

1. Request previous-release qualification evidence for both fixtures.
2. Inspect the evidence basis and capability report.

### Expected outcome

- The successor requires an executed upgrade from its actual previous W release.
- The initial release records predecessor absence and an explicit unexercised upgrade obligation; a fresh install cannot be labeled an upgrade pass.

### Evidence to retain

- Release-history basis and qualification reports for both predecessor states.

## AC-028-B02 — Bind apply to the exact reviewed snapshot and destination version

- Family: `AC-028`
- Type: `boundary`
- Profiles: `website`
- Requirements: `CMS-021`
- Layers: `real-provider-integration`, `migration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`, `AC-012`, `AC-031`

### Profile scope

- `website`: W previous-release upgrade and version-1 content-package portability, including stable mappings, dependencies, collisions, interruption and failed activation. First-release absence of a predecessor is recorded explicitly.

### Preconditions

- A dry-run plan binds a package digest, renderer versions and destination version tokens; it includes one update and retains an omitted existing page.

### Steps

1. Apply an unchanged reviewed plan in one fixture.
2. In independent fixtures change one source byte after review, change one destination version, or change a renderer version before apply.

### Expected outcome

- The unchanged plan applies once and retains the omitted page.
- Every changed fixture reports a stale-plan conflict and requires a new dry run; no partial authoritative apply occurs.

### Evidence to retain

- Plan bindings, source/destination fingerprints, conflict diagnostics and retained-page comparison.

## AC-028-P01 — Upgrade the actual previous website release

- Family: `AC-028`
- Type: `positive`
- Profiles: `website`
- Requirements: `CMS-021`, `CMS-022`, `CMS-023`, `FND-011`, `OPS-012`, `JRN-007`
- Layers: `real-provider-integration`, `migration`, `operational-recovery`

### Profile scope

- `website`: W previous-release upgrade and version-1 content-package portability, including stable mappings, dependencies, collisions, interruption and failed activation. First-release absence of a predecessor is recorded explicitly.

### Preconditions

- The previous supported W release is deployed with two types, three revisions per page, a blog post, two documentation versions, custom compatible renderer code, media, route redirects and stable import mappings. A coordinated backup and supported upgrade plan exist.

### Steps

1. Record both exact release identities and run preflight and the supported upgrade.

### Evidence to retain

## AC-028-P02 — Round-trip a package through reviewed import

- Family: `AC-028`
- Type: `positive`
- Profiles: `website`
- Requirements: `CMS-021`
- Layers: `real-provider-integration`, `migration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`, `AC-012`, `AC-031`

### Profile scope

- `website`: W previous-release upgrade and version-1 content-package portability, including stable mappings, dependencies, collisions, interruption and failed activation. First-release absence of a predecessor is recorded explicitly.

### Preconditions

- A W site contains versioned types, selected revisions, media, taxonomy, navigation, redirects and two pinned documentation versions. A fresh destination has matching renderer versions and prequalified site binding.

### Steps

1. Export the selected content as a version-1 package and capture its digest.
2. Dry-run on the destination, review stable-key mappings, apply, then export the imported selection again.
3. Repeat the completed apply using its original operation identity.

### Expected outcome

- Round-trip semantic content, fields, body order, references, routes and media hashes match; destination database ids may differ.
- Repeated apply returns its recorded result without duplicate revisions or mappings, and import alone does not publish.

### Evidence to retain

- Both package digests, semantic comparison, reviewed plan, per-item outcomes and mapping/revision counts.

## AC-028-R01 — Resume an import and recover from failed publication activation

- Family: `AC-028`
- Type: `recovery`
- Profiles: `website`
- Requirements: `CMS-021`, `CMS-022`
- Layers: `real-provider-integration`, `migration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`, `AC-012`, `AC-031`

### Profile scope

- `website`: W previous-release upgrade and version-1 content-package portability, including stable mappings, dependencies, collisions, interruption and failed activation. First-release absence of a predecessor is recorded explicitly.

### Preconditions

- A reviewed package updates two drafts and stages one media version. manifest-1 remains active and compatible; operation-1 identifies the reviewed plan.

### Steps

1. Interrupt once after media staging before database commit and, in a separate run, after database commit before acknowledgement.
2. Reconcile operation-1 before retrying and inspect per-item outcomes.
3. Attempt publication with a fault before activation commit, then recover using the retained validated manifest.

### Expected outcome

- Uncommitted authoritative changes roll back; a committed apply returns its original result without duplication.
- Staged media is accounted for and only unreferenced staging is cleaned. Failed activation preserves manifest-1 and its usable media/revisions.

### Evidence to retain

- Two checkpoint reports, mapping/revision counts, staging reconciliation, immutable manifest hashes and recovery result.

## AC-028-R02 — Recover a failed application upgrade through its supported plan

- Family: `AC-028`
- Type: `recovery`
- Profiles: `website`
- Requirements: `CMS-021`, `CMS-022`, `CMS-023`, `FND-011`, `OPS-012`, `JRN-007`
- Layers: `real-provider-integration`, `migration`, `operational-recovery`
- Security dependencies: `AC-003`, `AC-004`, `AC-012`, `AC-031`

### Profile scope

- `website`: W previous-release upgrade and version-1 content-package portability, including stable mappings, dependencies, collisions, interruption and failed activation. First-release absence of a predecessor is recorded explicitly.

### Preconditions

- The previous W release and its coordinated backup include custom content, stable mappings and historical media; the target upgrade has a documented forward-repair or restore path.

### Steps

1. Inject migration failure at its recorded checkpoint and retain the diagnosis.
2. Execute the supported recovery plan and read the restored or repaired application's published and historical content.

### Expected outcome

- Recovery reaches a coherent supported application/schema pair with retained data and custom-content behavior.
- Progress names the failed migration and repair outcome; no untested destructive reversal is assumed.

### Evidence to retain

- Exact release/backup identities, checkpoint and recovery records, content/mapping comparisons and restored application reads.
